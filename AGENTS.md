## Architecture conventions

- Proposed stack is React + TypeScript + Vite, D3 SVG helpers, FastAPI, pandas and Parquet. Validate feasibility during the approved milestone; do not add services or packages without a concrete need.
- Keep frontend and backend in separate top-level folders. Separate ingestion/preprocessing from request handling. Backend loads prepared data once via lifespan and serves JSON over HTTP.
- Keep API configuration centralized. Pin dependencies and record exact install/start commands and ports in README. Localhost is acceptable; do not deploy or publish just because hosting tools are available.
- React owns the app shell and shared selection state. Each reusable D3 module owns the contents of one isolated chart container, including marks and brushes; a thin React wrapper mounts, updates and cleans it up. React and D3 must never mutate the same descendants. Charts receive data and callbacks; they never fetch data or update each other directly.
- One typed selection state controls origin, exact weekday/hour tuple set, and optional animation state. Follow the interaction matrix and playback conflict rules in PROJECT_SPEC.md.
- Use stable IDs, count-based aggregates, explicit response schemas, cancellation/stale-response protection, and visible loading/error/empty states. Avoid requests on every brush movement.

## Keep code simple and readable

Keep the reader, cleaning rules, historical join and aggregation visible in short executable notebook cells, with raw/intermediate tables, issue counts, before/after totals and reasons for decisions for all three months. A few small helper functions are acceptable to repeat the same monthly steps without duplicating a large pipeline. The unchanged M1 script and Parquet files are historical evidence; the notebook does not need them to execute. Main chart cells show their filter/grouping and render from current DataFrames using the shared D3 modules. Do not load exported SVG/PNG files as notebook chart inputs. Notebook-only exploration may use Matplotlib and does not add production dashboard features.

- Prefer straightforward functions, descriptive names and small modules with one clear purpose. Write code the student can read, explain and maintain.
- Reuse the same D3 source for notebook previews and the app. Keep data loading separate from rendering, using plain data objects and callbacks.
- Avoid generic chart engines, plugin systems, unnecessary classes, extra state libraries and speculative configuration. Add an abstraction only when current code has a concrete need for it.
- Use brief comments for non-obvious decisions, especially metric rules and selection behavior. Preserve necessary correctness checks and cleanup without adding unrelated infrastructure.

## Data correctness

Never assume candidate field names are actual downloaded headers. Inspect actual schemas, historical airport keys and join cardinality. Preserve immutable raw inputs and provenance, checksums, exclusion counts and reproducible preprocessing commands. Do not silently pick the first coordinate duplicate or merge airports solely on ambiguous codes.

Late rate uses eligible completed non-diverted flights with known arrival status. Cancellation rate uses scheduled flights with the unknown-flag policy in the specification. Never treat missing as on time or zero; return null for zero denominators. Sum numerators/denominators before division. Scheduled local departure time is not actual departure time or UTC. Reporting carrier is not marketing carrier.

Do not invent findings, sample sizes, successful tests, performance numbers, or source availability. Label synthetic test fixtures and keep them out of production data. Retain counts and sparse-data indicators. Qualify observational comparisons for route mix, period and coverage.
